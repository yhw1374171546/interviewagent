### 5. 真实 LLM 评测（2026-08-14，DeepSeek v4 flash，30 样本）

**背景**: 简历/报告里的「追问贴题率 100%」「MAE 0.94」多为 Mock 或早期小样本数据。
B 组任务用真实 API 全量重测，补齐「真实 30 样本」证据，mock 与真实双口径并存。

**judge_eval.py 真实 30 样本 × 3 次评估（90 次调用）**:

| 指标 | Mock（框架验证） | **真实 LLM（本次）** | 说明 |

### 7. Agent 失败注入评测（2026-08-15，DeepSeek v4 flash，5 故障场景）

**背景**: 工具调用评测测「能力上限」，失败注入评测测「降级行为」（混沌测试）——
工具故意故障（瞬时失败/持续失败/超时/坏数据），验证 Agent 不崩溃、不无限重试、优雅降级。

| 指标 | 真实结果 |
|------|:---:|
| 无崩溃率 | **100%**（5/5 场景） |
| 循环检测兜底 | 坏数据场景触发（LLM 反复重试坏数据 → 3 次终止） |
| 持续失败降级 | ✅ 优雅降级（诚实告知 + 建议，不无限重试） |
| 超时处理 | ✅ 正常完成（3 秒慢响应） |
| 瞬时失败恢复 | LLM 放弃重试（诚实告知失败）——LLM 行为，非 bug |

> 复现: `python eval/failure_injection_eval.py`（真实，约 2 分钟）/ `--mock`（框架验证）。
> 测试还暴露并修复了循环检测的设计缺陷：失败重试（合法）曾被误判为循环，
> 现改为「失败不计入成功信号 + 连续失败 3 次单独兜底」。

**叙事口径**: 「Agent 健壮性做了混沌测试：5 个故障场景无崩溃率 100%，坏数据场景循环检测兜底；
测试还发现并修复了循环检测误杀失败重试的设计缺陷」——「测过失败路径」是最硬的工程素养证据。

### 9. 评分校准评测（2026-08-15，DeepSeek v4 flash，30 样本）

**背景**: 真实评测发现 LLM 对高分档系统性低估（人工 8.6 vs LLM 6.4）。多评委仲裁解决随机性
（std -36%），评分校准用「命中率 vs LLM 评分」的确定性规则解决系统性偏差。

| 指标 | 单评委 | +多评委 | **+校准** | 累计 |
|------|:---:|:---:|:---:|:---:|
| MAE | 1.2 | 1.15 | **0.76** | **-37%** |
| Pearson | 0.773 | 0.777 | **0.952** | +0.179 |
| 一致性 std | 0.22 | 0.14 | 0.2 | 稳定 |
| 追问贴题率 | 97% | 97% | 100% | +3pp |

> 校准规则: 命中率 ≥0.7 但 LLM 评分 <7 → 加分（低估）；命中率 ≤0.3 但评分 ≥7 → 减分（高估）；
> 幅度 = 期望分-实际分，封顶 ±2，钳制 [1,10]。
> 复现: `python eval/judge_eval.py --calibrate`（真实，约 15 分钟）。

**叙事口径**: 完整闭环——评测发现问题（高分低估）→ 多评委压随机性 → 校准压系统性偏差 →
重测验证 MAE 1.2→0.76（-37%）。每一层都可归因，这是「评测驱动改进」的完整叙事。

### 8. 多评委仲裁评测（2026-08-15，DeepSeek v4 flash，30 样本）

**背景**: 单评委评估对高分档系统性低估（人工 8.6 vs LLM 6.4，MAE 2.17）。多评委仲裁
（双评委并行 + 分歧仲裁）从机制上压缩评分偏差与随机性。

| 指标 | 单评委 | **多评委仲裁** | 变化 |
|------|:---:|:---:|:---:|
| 一致性 std | 0.22 | **0.14** | **-36%** |
| MAE | 1.2 | **1.15** | -4% |
| Pearson | 0.773 | **0.777** | +0.004 |
| 追问贴题率 | 97% | 97% | 持平 |

> 复现: `python eval/judge_eval.py --multi-judge`（真实，约 30 分钟；`--mock` 验证框架）。
> 成本: 每题 2-3 次调用（双评委 + 分歧才仲裁），`CostBudget` 兜底。
> 叙事: 多 Agent 不是炫技——先用评测发现问题（单评委偏差），再用多评委机制性解决，重测验证。

**叙事口径**: 「真实评测发现单评委评分随机性 std 0.22，多评委仲裁后降到 0.14（-36%）——
双评委并行、分歧大时仲裁裁决。多 Agent 的合理用法是『先有问题，再有解法』。」

## 三、指标设计审视（本轮修了什么、为什么）

1. **judge_eval 追问贴题率 → 改测 FollowUpAgent**：项目已 Agent 化，追问来源是 Agent 而非评估器；
   不改的话 Mock 下测的是通用话术（0%），与真实行为不符。
2. **benchmark "other" 阶段 → 明确为 follow_up_agent**：FollowUpAgent 的调用此前归入 "other"，
   无法解释调用次数变化；现在明确标注"追问自主决策（Agent 化，贴题率 100%）"。
3. **feature_eval 参考答案"要点覆盖率" → 改用"信息密度"**：初版用题库 expected_points 词表衡量
   面经答案（After 反而下降 66.7% vs 98.9%）——面经覆盖自己的要点，不是题库词表，指标对 RAG 不公平。
4. **单场 LLM 调用 6→10 的叙事**：如实标注 +4 次为追问决策，成本换自主性（贴题率 100%），
   不回避 Agent 化的代价。
