# 从 0 实现一个面试 Agent：混合架构、双引擎评分与容错设计

> 一个面向「秋招面试」的 AI 模拟面试系统，从架构选型到评测闭环的完整复盘。
> 代码已开源，所有指标可用 `python benchmark.py` 复现。

---

## 1. 为什么做这个项目

海投简历 → 收到面试 → 不知道会问什么 → 紧张发挥失常 → 挂了。这是每个秋招人的痛点。

传统解法都有硬伤：找朋友 mock 不专业、看面经和实际 JD 脱节、付费模拟贵且时间不灵活。

我想做的是一台「面试模拟器」：**把你投的 JD 贴进去，Agent 自动解析技术栈和考察重点，出针对性题目，对你的回答实时打分 + 深度追问，最后出一份评估报告。**

这个项目最有价值的地方不是「调用大模型」，而是**如何用工程手段让大模型变得可靠、可评估、可控成本**——这也是 LLM 应用工程师的核心能力。

---

## 2. 架构总览：规则引擎打底，LLM 做增量

```
JD 文本
   │
   ├─→ 规则引擎（200+ 关键词）   ← 确定性、0 成本、可复现，覆盖 70-90%
   ├─→ LLM 兜底（只传未匹配片段）← 语义理解，覆盖剩余 10-30%
   │
   └─→ JDAnalysis → 题库检索 → 题目 → 回答 → 双引擎评估 → 追问/报告
```

**核心设计原则：能规则化的绝不调 LLM。**

原因很朴素——LLM 调用有三个代价：

1. **成本**：每次调用都是真金白银；
2. **延迟**：推理模型先思考后作答，一次 5-20 秒；
3. **不确定性**：同样的输入可能得到不同输出，难以测试和复现。

所以我把「技能提取」「题库匹配」「关键词打分」这些确定性工作交给规则引擎，LLM 只处理规则搞不定的语义部分（职责描述、考察重点推断、深度/结构评分、追问措辞）。

实测效果：单场 8 题面试只有 6 次 LLM 调用（纯 LLM 方案约 7 次），且 JD 解析只传未匹配片段，输入 token 减少约 70%。

---

## 3. 双引擎评分：关键词算「对不对」，LLM 算「好不好」

评分是面试系统的灵魂。直接让 LLM 打分有个致命问题：**LLM 有「看起来不错就给高分」的 bias**，而且无法解释。

所以我拆成两个引擎：

| 引擎 | 负责 | 特点 |
|------|------|------|
| 关键词匹配 | 正确性、相关性 | 客观、确定、可解释（命中了哪几个要点） |
| LLM 语义分析 | 深度、结构、追问决策 | 只分析「表达质量」，不让 LLM 自己打分 |

综合分 = 正确性×35% + 深度×25% + 结构×20% + 相关性×20%。

这个设计还带来一个附带好处：**关键词匹配天然提供「可解释性」**——报告里能告诉用户「你命中了 X 个要点，漏掉了 Y」，而不是一句玄学的「8 分」。

### 中文关键词匹配的坑

这块踩了项目里最大的一个坑。评测发现高分回答被系统性低估（MAE 2.63）。定位到三个问题：

1. `B+树结构` 拆词后单字母 `b` 被过滤 → 永不命中；
2. 中文连续串要求整串相等（`范围查询优势`），真实回答不会逐字复述；
3. 单关键词要点阈值 `max(1, 0.5)=1.0` 要求完美命中。

**根因是中文没有天然分词边界**——整串匹配太严、字级匹配太松。最终折中方案是「字符覆盖率」：中文长词（≥4 字）按字符覆盖率 ≥60% 视为命中。

修复后 MAE 1.50 → **0.94**，Pearson 0.923 → **0.991**。

## 4. 容错设计：让大模型变得「可用」

大模型 API 是出了名的不稳定：限流 429、超时、连接错误、返回格式错误。面试是长链路，一次中断就前功尽弃。

四层容错：

1. **指数退避 + 抖动**：`base_delay * 2^attempt`，加 50%-150% 随机抖动防惊群；
2. **熔断器（三态）**：连续失败 N 次进入 OPEN 直接拒绝，冷却后 HALF_OPEN 探测，连续成功恢复 CLOSED；
3. **降级链**：主模型挂了 → 备用模型 → 规则引擎；
4. **输出校验**：JSON Schema 校验 + `repair_truncated_json`（尾部回退补齐括号，抢救推理模型被 max_tokens 截断的 JSON）。

还有个容易被忽略的细节：**SDK 懒加载**。`core/llm.py` 不顶层 import openai/anthropic，只在真正实例化 client 时导入。这样无 Key 环境（CI、Demo）不装 SDK 也能跑，测试全离线。

## 5. 模型路由：快模型打底，强模型点睛

真实联调发现：推理模型（deepseek-v4-pro）先输出 `reasoning_content` 再作答，**单次评估 17.6 秒**，创建面试 51 秒。这个体验没人能忍。

解法是「模型路由」——按任务重要性分配不同模型：

- **flash（快模型）**：评估、JD 解析、暖场、出题（高频，对延迟敏感）；
- **pro（强模型）**：最终报告（关键节点，对质量敏感）。

配合出题/暖场的 `asyncio.gather` 并行，单次评估降到 **5.4 秒**（3.3 倍），创建面试 51s→22.1s，而评语质量无下降。

**经验：推理模型不适合高频小任务。模型路由是 LLM 应用成本/延迟优化的第一课。**

---

## 6. 可观测性：测不到就优化不了

接入了调用级埋点：每次 LLM 调用的延迟、prompt/completion token、成本，按阶段聚合，随会话快照持久化，Web 面试结束自动出「本场统计」卡片。

这套东西立刻体现价值：一次实测发现评估阶段 310 秒（平均 20s/次），和之前的 5.4s 差异巨大，日志确认无重试——是 API 端延迟波动。**没有这套指标，这类问题完全不可见。**

---

## 7. 评测闭环：LLM-as-judge

面试官必问：「你怎么评价自己的系统？」

答案不是「我感觉不错」，而是一套量化闭环：10 题 × 高/中/低三档人工标注（30 样本），三项指标——评分一致性（同答评 3 次 std）、准确性（MAE + Pearson vs 人工标注）、追问贴题率。

评测的最大价值不是「证明系统有多好」，而是**暴露盲区**。这次发现的高分低估问题，在日常使用中完全无感，只有和 ground truth 对比才显形。

---

## 8. Streaming：从「干等 45 秒」到「逐字流式」

真实报告生成实测 45 秒，用户对着空白页面干等。接入 SSE 流式后，报告文字逐字显示，评估 JSON 保持整块返回（结构化数据不适合流式）。

实现上有个关键点：**流式重试只能在首块到达前**——首块已经发出后再重试，会向客户端重复输出已显示的文字。这是流式与普通重试的本质区别。

---

## 9. 写在最后：三个最值得带走的东西

1. **「混合架构」思维**：大模型不是银弹，确定性工作交给规则，LLM 只做增量——这是成本、延迟、可测性的最优解。
2. **「评测驱动」而非「感觉驱动」**：没有 ground truth 对比，你永远不知道自己的系统哪里有问题。
3. **「可靠性工程」是 LLM 应用的护城河**：重试、熔断、降级、可观测性，这些才是让 demo 变产品的东西。
